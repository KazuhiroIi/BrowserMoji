# ASCII Camera アーキテクチャ・設計方針（v0.2）

要件は [requirements.md](./requirements.md) を参照。本書は「どう作るか」のうち、**変更に強くするための土台**と、**実験で決める事項**をまとめる。

状態の凡例は requirements.md と同じ（🔒確定 / 🔶仮決め / ❓未決）。

## 1. 設計原則

1. **段階を分ける**: 変換処理を独立した段階に分け、各段階の実装を差し替え可能にする（N-3）
2. **設定を 1 か所に集約する**: 調整可能な値はすべて 1 つの設定オブジェクトに入れ、UI・保存・実験が同じ設定を読む
3. **基準実装を持つ**: 最適化実装（GPU など）の正しさは、CPU の基準実装との比較で確認する（N-4）
4. **実機計測を先に行う**: 性能に関わる選択（描画方式など）は、推測ではなく実機での計測で決める
5. **決めたことは記録する**: 設計判断は `docs/decisions/` に 1 判断 1 ファイルで残す（背景・選択肢・決定・理由）

## 2. 処理パイプライン 🔒

```
カメラ取得 → 前処理（縮小・セル分割） → 特徴量計算 → 文字選択 → 描画
                                         ↑                  ↑
                                  (輝度・勾配)       (色付け: 後から差し込む)
```

差し替えを想定する境界（TypeScript のインターフェース案）:

```ts
// 1セルぶんの特徴量
type CellFeature = {
  luminance: number;       // 平均輝度 0..1
  gradMagnitude: number;   // 勾配の強さ
  gradAngle: number;       // 勾配の向き（ラジアン）
  // 将来拡張: color, segmentClass, 領域内の濃淡パターン など
};

interface FeatureExtractor {
  extract(frame: FrameSource, grid: GridSpec, cfg: AppConfig): CellFeature[];
}

interface GlyphSelector {
  select(features: CellFeature[], cfg: AppConfig): Uint16Array; // 各セルの文字ID
}

interface Renderer {
  render(glyphIds: Uint16Array, grid: GridSpec, cfg: AppConfig, color?: Uint8Array): void;
}
```

実装を GPU に移す場合は段階が融合する（特徴量計算と文字選択を同じシェーダで行うなど）。その場合も、**入出力の意味は上記と同じ**に保ち、基準実装との比較テストが書けるようにする。

## 3. 文字選択方式（実験で決める） ❓

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | セルの平均輝度で文字の濃さを決める。勾配が十分強ければ、勾配の向きに合う線の文字に置き換える | 単純で軽い。調整しやすい | 文字の形と画像の細部の一致は弱い |
| B | 文字ごとの特徴量（濃さ、ストロークの向き、セルを分割した各領域の濃淡など）を事前計算し、セルの特徴量と最も近い文字を探す | 文字の形が画像に沿う。参考にしている AA に近づけやすい | 計算量が多い（候補文字数 × セル数 × 特徴量の次元） |

どちらも `GlyphSelector` の実装として並べ、見た目と処理時間で比べる。B は特徴量の次元を小さく抑え、GPU で並列化する前提で検討する。

## 4. 文字の見た目の扱い（グリフアトラス） 🔶

- 全角文字を DOM のテキストで描くと、端末ごとの既定フォント・字幅の差でグリッドが崩れる恐れがある（N-5）
- **ビルド時にフォントから文字を画像化**し、グリフアトラス（画像）と文字ごとの特徴量テーブルを生成する。実行時はこれらの資産を読み込むだけにする
- 生成ツールは Python で書き、アルゴリズムの試作（実験）と同じコードを共有する
- 使用するフォントのライセンスを確認し、リポジトリに記録する

## 5. 描画方式の候補 ❓

| 方式 | 長所 | 短所・懸念 |
|---|---|---|
| DOM（`<pre>` 等） | 実装が最も簡単。テキストをそのままコピーできる | 更新が重く、全角文字のグリッドが端末依存で崩れやすい |
| Canvas 2D（アトラスから転写） | 端末非依存にしやすい。実装が比較的容易 | CPU 側で特徴量計算をすると重い |
| WebGL2 | 特徴量計算・文字選択・描画を GPU に載せられ、最も高い fps が期待できる | 実装が複雑。端末ごとの挙動差の確認が必要 |

- 基準（最低限動かす）は WebGL2 とし、WebGPU は対応状況が端末ごとに異なるため採用しない 🔶
- 結論は実験 EXP-1 の結果で `docs/decisions/` に記録する

## 6. カメラ取得で押さえる点（要検証）

- `getUserMedia` は HTTPS と、利用者の操作（ボタン押下）の後の呼び出しを前提にする
- iOS Safari では、`<video>` に `playsinline` と `muted` が必要になる。フルスクリーン化されないようにする
- 背面カメラは `facingMode: "environment"` を指定する。端末によっては取得できない場合があるため、フォールバックを用意する
- フレーム取得は、`requestVideoFrameCallback` が使えれば使い、無ければ `requestAnimationFrame` で代替する
- 画面回転時は、映像の向き・アスペクト比・セル数を再計算する
- 取得解像度は要求値と実際の値が異なることがあるため、実際の値を読み取ってから処理する

## 7. 配信とオフライン 🔶

- 配信は GitHub Pages（N-6）。**リポジトリ名のサブパス**（`/<repo>/`）で配信されるため、ビルド設定のベースパスと Service Worker のスコープを合わせる
- オフライン対応（N-2）は Service Worker でアプリ本体の資産をキャッシュする
- **更新の反映**: 古いキャッシュが残って新しい版が出ない事故を避けるため、バージョン付きキャッシュと、更新検知・再読み込みの手順を決めておく
- セグメンテーション用モデルなど大きな資産は、機能を有効にしたときだけ読み込む（P-5）

## 8. セグメンテーション（F-17）の構想 🔶

- 使用候補: Ultralytics の **YOLO26-sem**（セマンティックセグメンテーション。`yolo26n-sem` などのスケールがある）
- 公式ドキュメントでは、セマンティックセグメンテーションの評価に **Cityscapes**（街路シーン）が使われている。屋内や自然景観では、期待どおりに分類されない可能性があるため、実機の映像で品質を確認する
- ブラウザでの実行は、モデルを ONNX 等にエクスポートし、ブラウザ向けの推論ランタイム（WASM / WebGL / WebGPU のいずれか）で動かす想定。端末負荷が大きいため、**描画ループとは非同期に低頻度（数 fps）で推論**し、結果のマスクを拡大して使う
- 主処理（30fps / 15fps の要件）を妨げないことを必須条件とし、満たせなければ採用しない
- **ライセンス**: YOLO26 のコード・モデルは AGPL-3.0 とエンタープライズライセンスの二本立てで公開されている（公式ドキュメントの記載）。ソース公開のリポジトリで使う場合の扱いは、公式のライセンス文書を確認して判断する（Q-2）

## 9. リポジトリ構成案

- ビルド: Vite + TypeScript、UI フレームワークなし 🔶
- Python ツール: 仮想環境で依存を固定する（`tools/` 配下に README と依存定義を置く）

```
/
  docs/                  # 本書、requirements.md、decisions/、experiments/
  src/                   # Web アプリ本体（TypeScript）
    pipeline/            # FeatureExtractor / GlyphSelector / Renderer と各実装
    camera/              # カメラ取得、回転対応
    ui/                  # 開始画面、設定パネル
    i18n/                # UI 文言（言語ごとの辞書）
    config.ts            # AppConfig の定義と既定値
  tools/
    prototype/           # Python による試作・実験（文字選択方式の比較など）
    atlas/               # グリフアトラスと特徴量テーブルの生成
  public/assets/         # 生成済みアトラス、特徴量テーブル
```

## 10. 実験一覧

結果は `docs/experiments/` に、条件・数値・結論を短く残す。

| ID | 目的 | 判定基準 | 決まること |
|---|---|---|---|
| EXP-1 | 描画方式ごとの fps を、低スペック端末と標準端末で計測 | P-1・P-2 を満たすか | 描画方式（§5） |
| EXP-2 | 文字選択方式 A と B の見た目・処理時間の比較（PC 上の Python） | 見た目の評価と計算量 | 文字選択方式（§3） |
| EXP-3 | 文字セット候補（ひらがな、カタカナ、記号、少数の漢字など）の見た目の比較 | 濃淡の階調の幅、エッジ表現の質 | T-4、Q-7 |
| EXP-4 | iOS／Android での、カメラ取得・回転・権限の挙動確認 | §6 の各項目が動作するか | カメラ周りの実装方針、E-2 の対応範囲 |
| EXP-5 | YOLO26-sem のブラウザ上での速度・品質確認 | 描画ループを妨げず、実用的な精度か | F-17 の採否、Q-2 |

## 11. 技術的なリスク

| リスク | 対策 |
|---|---|
| 低スペック端末で 15fps に届かない | 早期に EXP-1 を実施。GPU への移行、特徴量の次元削減、解像度の自動調整（F-16） |
| iOS Safari 固有の挙動で動かない | EXP-4 を早期に実施。§6 のチェックリストで確認 |
| 全角文字の表示が端末で崩れる | グリフアトラス方式（§4） |
| 方式 B の計算量が大きすぎる | 特徴量の次元削減、候補文字数の削減、方式 A への切り替え |
| 古い Service Worker のキャッシュで更新が反映されない | §7 の更新手順を実装時に決める |

## 12. 多言語対応（UI） 🔒

- UI の文言はすべて `src/i18n/` の辞書に置き、コード中に直接書かない（N-9）
- v1 は日本語のみを提供する。辞書の型（キーの一覧）を 1 つ定義し、言語を追加するときは同じキーの辞書を足すだけで済むようにする
- 言語の決定順（将来）: 利用者の明示的な選択 → ブラウザの言語設定 → 日本語
- UI の文字は端末のシステムフォントで表示する（外部フォントは読み込まない。N-1）。アスキーアートの文字はグリフアトラスで描くため、UI の言語とは無関係（T-7）
- 数値・単位の表記は言語依存の整形を避け、文言側で組み立てる
