# D-002: 生成物の契約① — アトラスは PNG、特徴量テーブルは JSON

- 状態: 🔶（仮決め・方式 B 実験後に見直す）
- 関連: architecture.md §3, §4, D-001

## 背景

グリフアトラス（画像）と、文字ごとの特徴量テーブルは、Python 側の生成ツール（tools/atlas/）と Web 側（Renderer / GlyphSelector）の取り決め（契約）になる。形式を先に固定しておかないと両トラックの作業が並行できない。

## 選択肢

1. **アトラス: PNG／特徴量テーブル: JSON**: 汎用で、デバッグも容易
2. アトラス: WebP／特徴量テーブル: バイナリ（MessagePack 等）: 小さいが扱いにくい
3. 両方を 1 つの JSON に base64 埋め込み: 単一ファイルだがサイズ・可読性が悪い

## 決定

- アトラスは **PNG**、特徴量テーブルは **JSON** とする
- 特徴量テーブルのフィールド（初期案）:
  - `charID`: アトラス上のグリフの ID（描画時のインデックス）
  - `char`: 文字（1 文字）
  - `ink`: 濃度（平均インク率、0..1）
  - `edgeStrength[8]`: 8 方向の線分強度
  - `pattern[4][4]`: セルを 4×4 に分割した各領域の濃淡（0..1）
- フィールドは**方式 B（architecture.md §3）の実験後に増減する**。スキーマにはバージョンを設ける

## 理由

- PNG・JSON はブラウザ・Python の双方で追加依存なしに扱え、人間が確認できるため実験が速い
- 特徴量は方式 B の前提設計（§3）であり、EXP-2 の結果で必要な次元が確定する。確定後に凍結する
