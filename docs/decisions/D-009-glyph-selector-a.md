# D-009: 文字選択方式は方式 A（輝度＋エッジ線文字）を採用する

- 状態: 🔒（確定）
- 関連: architecture.md §3・§10, EXP-2, D-002（特徴量テーブル契約）, N-4

## 背景

architecture.md §3 は文字選択方式として 2 案を挙げていた:

- **方式 A**: セル平均輝度 → 濃度文字、エッジセル（最大勾配 ≥ しきい値）は
  勾配の向きに合う線文字へ置換
- **方式 B**: 文字ごとの特徴量 [density(1), dir8(8), region4(16)] との
  重み付き最近傍

EXP-2（docs/experiments/exp-2.md）で、両方式を Python の CPU 基準実装として
実装し、合成画像 4 枚 → 実機写真 15 枚（face / high_contrast / room / scene）で
見た目と 1 フレーム処理時間を比較した。見た目の評価はユーザー（15 枚すべて）と
エージェント（10 枚）が独立に行った。

## 選択肢

1. **方式 A を採用する**
2. 方式 B を採用する（GPU 並列化を前提とする）
3. 両方を実装し、実行時に切り替え可能にする

## 決定

- **方式 A を v1 の `GlyphSelector` 実装として採用する**
- 方式 B は不採用。ただしアルゴリズム・実装（selector.py）は基準実装として
  残し、将来 GPU 側で 25 次元距離計算が実質無料になった場合の再評価の
  選択肢として記録に留める
- 調整の着手点（しきい値・テクスチャ抑制・暗部の前処理・featurePx・列数）は
  exp-2.md 結論に記録した通り

## 理由

EXP-2 の実機写真での評価より:

- **見た目**: 合成画像では B が「形が沿う」と評価されたが、実機写真では逆転し、
  **A のほうが形・輪郭を捉える**。B は濃度が近い複数の物体を同じ文字の塊に
  混合し（face2/face3/room2）、平滑域が反復テクスチャ + 散在ノイズになり、
  手書き図面（high_contrast4）や夜景（scene3/scene4）の構造がほぼ消失した。
  15 枚すべてのユーザー評価と 10 枚のエージェント評価が同じ方向
- **計算量**: B は A の約 11〜12 倍（7 回平均、合成・実機写真とも一致）。
  A は 80 列で 16〜55 ms / 120 列で 64〜66 ms（PC/CPU）。Web 本番は GPU 前提
  とはいえ、B を採ぶ見た目上の利点が確認できなかったため、コストを払う
  理由がない
- **選択肢 3（両方実装）**: インターフェース（`GlyphSelector`）は既に差し替え
  可能な契約なので、B を復活させる場合はその時点で追加すればよい。
  v1 で両方を抱えるとチューニング対象が増え、Web 側の実装・検証コストが
  増すため採らない

A の既知の弱点（輝度が近い領域での輪郭途切れ、テクスチャへの過剰反応、
暗部同士の境界消失）は exp-2.md の結論に調整の着手点として記録した。
