# EXP-1: Web 実装（Canvas 2D）の実機 fps 計測 — 基準測定を記録（全列数の計測は継続）

状態: **基準測定（コミット 09cab47・列数 48・両端末）を記録済み。全列数の計測と判定は未完了**。
showFps ON のオーバーレイで、

実機での計測・転記と判定はユーザーが行う（architecture.md §10 の EXP-1）。

- 実装: fps オーバーレイ（`src/ui/fps.ts`。設定パネルの「fps 表示」で ON/OFF。既定 ON）

## 目的

Canvas 2D 版（D-004 の先行実装。CPU パイプライン + アトラス転写）の変換パイプライン全体の
実機 fps を測り、

- P-1（標準的な近年のスマートフォンで 30fps）・P-2（低スペック端末で 15fps 以上）を満たすかの判定
- どのステージ（前処理 blit / 前処理読み出し / 特徴量 / 文字選択 / 描画）がボトルネックかの把握

を行う。結果は描画方式の採否（architecture.md §5、D-004）と、後続の最適化の方針に使う。

## 判定基準

| 判定基準 | 基準値 | 出典 |
|---|---|---|
| P-1: 標準的な近年のスマートフォン（参照端末: moto g64 5g）で 30fps | 平均 fps ≥ 30 | requirements.md §4 |
| P-2: 低スペック端末（基準端末: OPPO A5 2020）で 15fps 以上 | 平均 fps ≥ 15 | requirements.md §4 |

最小 fps は判定の補助値とする（瞬間的な落ち込みの有無の確認用）。

## 計測プロトコル

1. OPPO A5 2020 を P-2 の基準端末、moto g64 5g を P-1 の参照端末とする
2. 列数は既定 48 を公式値とし、32 / 64 / 96 / 128 は参考カーブとする
3. カメラ設定とダミーアトラスは現状のまま（変数を増やさない）
4. 明るめの屋内シーンで計測する（暗所はカメラ自体が減速して fps が落ちるため）
5. 指標は平均 fps・最小 fps・ステージ別平均処理時間とし、各条件 30 秒以上観測する
6. 数値は端末画面のオーバーレイから手動で読み取り転記する

### オーバーレイの見方

| 行 | 意味 |
|---|---|
| avg | 直近 5 秒の瞬間 fps（1000/dt）の平均 |
| min | 同窓の瞬間 fps の最小 |
| cam | カメラ実効 fps（rVFC の metadata.presentedFrames の差分から算出。rAF フォールバックでは「—」） |
| pre / read / feat / sel / draw | 各ステージの同窓平均処理時間（ms）: 前処理 blit（video → work canvas の drawImage）/ 前処理読み出し（getImageData）/ 特徴量（extract）/ 文字選択（select）/ 描画（render） |
| cols | 現在の列数と描画方式名（例: `48 / canvas2d`） |

cam はカメラ自体の fps であり処理ループの fps ではない。処理が重いときは avg < cam になる
（逆に暗所で cam 自体が下がっていないかは ④ の確認に使う）。

## 中間観察（基準測定・列数 48 時点）

- 描画（draw）が最大のボトルネック（moto 27.0 ms / OPPO 44.6 ms）。次いで前処理 blit（pre）が重く、特に moto で大きい（16.2 ms）
- カメラ実効 fps（cam: moto 29.8 / OPPO 25.0）には余裕があり、前処理読み出し（read）・特徴量（feat）・文字選択（sel）は軽い
- ステージ別の合計（moto 約 44.6 ms / OPPO 約 53.0 ms）よりフレーム間隔（平均 fps の逆数。OPPO で約 61 ms）のほうが長く、毎フレームの固定オーバーヘッドが疑われる（OPPO で約 8 ms 分）
- 判定・結論と、対策実装の内容・効果はまだ書かない（対策後に再計測して追記する）
