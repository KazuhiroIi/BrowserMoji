# EXP-1: 描画方式ごとの実機 fps 計測 — 完了（描画方式は WebGL2 に決定）

状態: **実施済み（完了）**。基準測定（コミット 09cab47）・Canvas 2D 改善後（コミット 25f6678）・WebGL2（コミット b16ec8d 相当）の計測を記録し、判定済み。
showFps ON のオーバーレイで、
平均 fps・最小 fps・カメラ実効 fps・ステージ別の平均処理時間を表示できる。
実機での計測・転記と判定はユーザーが行った（architecture.md §10 の EXP-1）。

- 関連: architecture.md §5（描画方式）・§10（EXP-1）、requirements.md §4（P-1 / P-2 / P-3）、docs/decisions/D-004 / D-008
- 実装: fps オーバーレイ（`src/ui/fps.ts`。設定パネルの「fps 表示」で ON/OFF。既定 ON）
- 決定: 描画方式は **WebGL2**（docs/decisions/D-008-renderer-webgl2.md）

## 目的

Canvas 2D 版（D-004 の先行実装。CPU パイプライン + アトラス転写）の変換パイプライン全体の
実機 fps を測り、

- P-1（標準的な近年のスマートフォンで 30fps）・P-2（低スペック端末で 15fps 以上）を満たすかの判定
- どのステージ（前処理 blit / 前処理読み出し / 特徴量 / 文字選択 / 描画）がボトルネックかの把握

を行う。結果は描画方式の採否（architecture.md §5、D-004）と、後続の最適化の方針に使う。

## 判定基準

| 判定基準 | 基準値 | 出典 |
|---|---|---|
| P-1: 標準的な近年のスマートフォン（参照端末: moto g64 5g）で 30fps | 平均 fps ≥ 30 | requirements.md §4 |
| P-2: 低スペック端末（基準端末: OPPO A5 2020）で 15fps 以上 | 平均 fps ≥ 15 | requirements.md §4 |

最小 fps は判定の補助値とする（瞬間的な落ち込みの有無の確認用）。

## 計測プロトコル

1. OPPO A5 2020 を P-2 の基準端末、moto g64 5g を P-1 の参照端末とする
2. 列数は既定 48 を公式値とし、32 / 64 / 96 / 128 は参考カーブとする
3. カメラ設定とダミーアトラスは現状のまま（変数を増やさない）
4. 明るめの屋内シーンで計測する（暗所はカメラ自体が減速して fps が落ちるため）
5. 指標は平均 fps・最小 fps・ステージ別平均処理時間とし、各条件 30 秒以上観測する
6. 数値は端末画面のオーバーレイから手動で読み取り転記する

### オーバーレイの見方

| 行 | 意味 |
|---|---|
| avg | 直近 5 秒の瞬間 fps（1000/dt）の平均 |
| min | 同窓の瞬間 fps の最小 |
| cam | カメラ実効 fps（rVFC の metadata.presentedFrames の差分から算出。rAF フォールバックでは「—」） |
| pre / read / feat / sel / draw | 各ステージの同窓平均処理時間（ms）: 前処理 blit（video → work canvas の drawImage）/ 前処理読み出し（getImageData）/ 特徴量（extract）/ 文字選択（select）/ 描画（render） |
| cols | 現在の列数と描画方式名（例: `48 / canvas2d`） |

cam はカメラ自体の fps であり処理ループの fps ではない。処理が重いときは avg < cam になる
（逆に暗所で cam 自体が下がっていないかは ④ の確認に使う）。

d8369e5（WebGL2 版の実装）のデプロイでは、「開始」直後から canvas が一度も描かれず白画面となり、
fps オーバーレイも出ないため WebGL2 の計測は実施できなかった
（`ensureRenderer()` が初回フレームで Renderer を生成しない不具合）。本コミットで修正済み。
WebGL2 版の計測は次回セッションで実施した（上記「WebGL2」を参照）。

## 中間観察（Canvas 2D 改善後・列数 48 時点）

- OPPO A5 2020 では draw が 44.6 → 19.0 ms と半減したが、平均 fps は 16.3 → 16.2 とほぼ不変。フレーム時間（約 62 ms）とステージ合計（約 30 ms）の差が約 31 ms に拡大しており、計測外のオーバーヘッド（2D ラスタライズの滞留や合成待ち）が支配的と推定する
- moto g64 5g では draw が 27.0 → 27.5 ms とほぼ不変で、平均 fps も 20.7 → 20.6 とほぼ不変。1 呼び出しごとの転写コスト × 全セル数が支配的と推定する
- いずれの端末でも描画呼び出しを 1 回にまとめる（= WebGL2 の 1 draw call 化）ことで改善が見込める。これが期待解である
- 判定・結論と、WebGL2 版の効果は WebGL2 版の再計測後に下記「WebGL2」「判定」へ追記した

## 中間観察（基準測定・列数 48 時点）

- 描画（draw）が最大のボトルネック（moto 27.0 ms / OPPO 44.6 ms）。次いで前処理 blit（pre）が重く、特に moto で大きい（16.2 ms）
- カメラ実効 fps（cam: moto 29.8 / OPPO 25.0）には余裕があり、前処理読み出し（read）・特徴量（feat）・文字選択（sel）は軽い
- ステージ別の合計（moto 約 44.6 ms / OPPO 約 53.0 ms）よりフレーム間隔（平均 fps の逆数。OPPO で約 61 ms）のほうが長く、毎フレームの固定オーバーヘッドが疑われる（OPPO で約 8 ms 分）
- 対策としてセル実サイズに縮小したアトラスのキャッシュを導入した（コミット 25f6678。上記の「Canvas 2D 改善後」を参照）

## 判定

描画方式は **WebGL2** に決定した（docs/decisions/D-008-renderer-webgl2.md）。

| 判定基準 | 結果 |
|---|---|
| P-1: moto g64 5g で 30fps を満たすか | **達成**（avg 30.8。cam 29.9 fps のカメラ上限で頭打ち） |
| P-2: OPPO A5 2020 で 15fps 以上を維持するか | **達成**（大余裕。avg 29.2 / cam 25.0 fps） |

根拠:

- Canvas 2D は最適化後も draw 19〜27.5 ms に加え、OPPO では計測外の約 31 ms のオーバーヘッドがあり P-1 に届かない
- WebGL2（グリッドシェーダ・1 draw call）は draw 0.1〜0.3 ms で、両端末ともカメラの実効上限まで到達した（moto: cam 29.9 → avg 30.8、OPPO: cam 25.0 → avg 29.2）

決定の反映: AppConfig の `renderer` 既定を `'webgl2'` に変更。Canvas2DRenderer は CPU の基準実装（N-4）とフォールバックとして保持し、設定パネルの「描画方式」選択 UI も残す。

## 持ち越し事項

1. **特徴量計算の GPU 移行**: feat はセル数に比例して増大し、96 列以上で支配的になる（128 列で 20.2 ms）。特徴量計算の GPU 移行を検討する（architecture.md §2 の段階融合・EXP-2 方式 B の GPU 前提と整合）
2. **前処理 blit の軽減**: pre は moto で 16.3 ms と大きい。カメラ解像度の制限（`getUserMedia` への width/height 要求）をレバーとして検討する
3. **min fps のスパイク**: 両端末で min fps が約 10〜12 まで落ちるスパイクがある（原因未調査: GC・カメラジッタ等）
4. **iOS Safari の確認**: WebGL2・rVFC（`requestVideoFrameCallback`）の挙動は EXP-4 で確認する
