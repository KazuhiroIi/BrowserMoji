# EXP-2: 文字選択方式 A / B の比較（PC 上の Python）— 草稿

状態: **確定**。合成画像・実機写真 15 枚での比較と、ユーザー・エージェントによる
見た目評価を経て**方式 A を採用**（docs/decisions/D-009-glyph-selector-a.md）。

- 関連: architecture.md §3（方式 A/B）、requirements.md G-3 / F-3 / F-4 / P-1 / P-2
- 実装: `tools/prototype/`（selector.py / convert.py / bench.py、README 参照）

## 目的

文字選択方式 A（輝度 → 濃度文字＋勾配向きの線文字）と
方式 B（セル特徴量と文字特徴量の重み付き最近傍）を、
見た目と 1 フレーム処理時間で比較し、採用方式の候補を絞る。

## 条件

| 項目 | 値 |
|---|---|
| 実装 | Python 3.12.12 / numpy 2.5 / OpenCV 5.0（CPU 基準実装。最適化は未実施） |
| 入力 | 合成画像 4 枚（800×600 グレースケール）: 滑らかなグラデーション / 幾何図形 / 高周波の縞・市松・同心円 / 明暗差の大きいシルエット |
| セル | 正方形。列数 48 / 80 / 120（行数はアスペクト比から自動） |
| セル特徴量 | featurePx = 16（セルを 16×16 に縮小して計算） |
| 文字セット | 4 群すべて（212 文字、Noto Sans JP Regular で描画） |
| 重み（B） | density 1.0 / dir8 1.0 / region4 0.7（平滑セルでは dir8 を比較せず、線文字も除外。下記「実装上の発見」参照） |
| しきい値（A） | エッジ検出: セル内最大 \|Sobel\| ≥ 0.14、整合性 ≥ 0.25 |

## 方式の実装概要

- **A**: セル平均輝度 → 濃度記号（16 段階）の最近濃度を選ぶ。エッジセル
  （最大勾配 ≥ しきい値）は、勾配の向きに最も近い「まっすぐな線」記号へ置換。
  太さは勾配強度で段階選びする
- **B**: セル特徴量 [density(1), dir8(8), region4(16)] = 25 次元と、
  文字ごとに事前計算した同形式の特徴量（features.json）との
  重み付き二乗距離で全文字から最近傍を選ぶ

両方式とも、アトラス生成時に計算した**同じ**特徴量テーブルを使う
（アトラス生成と実行時で特徴量計算コードを共有 = Web 本番と同じ構造）。

## 結果 1: 処理時間（1 フレーム、7 回平均・ウォームアップ 1 回除去）

入力 `edges.png`（エッジが最多 = A の最悪ケース）:

| 列数 | セル数 | 前処理 | A 選択 | B 選択 | 描画 | A 合計 | B 合計 |
|---|---|---|---|---|---|---|---|
| 48 | 1,728 | 1 ms | 6 ms | 91 ms | 1 ms | **8 ms** | **93 ms** |
| 80 | 4,800 | 1 ms | 18 ms | 208 ms | 2 ms | **20 ms** | **211 ms** |
| 120 | 10,800 | 3 ms | 66 ms | 859 ms | 7 ms | **76 ms** | **869 ms** |

入力 `gradient.png`（エッジ最少 = A の最良ケース）:

| 列数 | セル数 | A 選択 | B 選択 |
|---|---|---|---|
| 48 | 1,728 | 6 ms | 90 ms |
| 80 | 4,800 | 19 ms | 209 ms |
| 120 | 10,800 | 54 ms | 673 ms |

- B はセル数にほぼ比例し、120 列でキャッシュ効率が落ちて超線形に増える
  （距離行列 = セル数 × 文字数 × 25 次元）。**B は A の約 10〜12 倍の計算量**
- A は 120 列でも 76 ms。エッジセルが少ない画像では 16〜20 ms 程度
- 描画（アトラスからのタイル転写）は 1〜7 ms と軽く、ボトルネックは選択処理
- 実行ごとのばらつきは ±10〜15% 程度ある（raw 値は out/bench*.json。最小値は
  A@120 で 39 ms まで下がる）。傾向としての結論はこの差では覆らない
- 数値は PC（CPU）のもの。目標 fps（P-1: 30fps / P-2: 15fps）の判定は
  Web 実装（GPU 前提）の EXP-1・実機計測で行う。ここでの値は**相対比較**用

## 結果 2: 見た目（合成画像、80 列中心）

出力: `tools/prototype/out/compare/<画像名>_c<列数>.png`（入力 / A / B を縦に並べた比較図）。

- **滑らかなグラデーション**
  - A: 濃度段階がはっきりした帯になり、隣接段階の境界で市松状のディザノイズ
    が出る。明部の丸い光は読み取れる
  - B: 濃度の再現は A より滑らか（段差が少ない）。ただし平滑領域で
    「田」「◎」「口」など均一な文字が連続し、グラフ用紙のような反復テクスチャ
    になる。濃度の近い文字が複数あっても形の近いものに偏る
- **幾何図形**: 両方式とも輪郭を捉える。B は円の縁で ╱ ╭ ┻ など
  構造文字を選び、A は向きに合う ╱ ╲ │ ─ で輪郭を描く。内側の塗りは
  A が ■ ● の単純な濃度表現、B は 黒田森 など濃度の近い漢字も混ざる
- **高周波（縞・市松・同心円）**: 80 列では縞 1 本 ≈ 2.3 セルで、どちらの方式も
  エイリアス気味。それでも A は縞の境界に ╱ ╲ の連鎖を作り（向きは正しい）、
  B は田・▲ などで濃淡を先に合わせる。市松は両方式とも中間調に潰れる
- **シルエット**: A は楕円の輪郭を ─ ╱ ╲ │ の線で描き、白い窓の四辺を
  ─ │ で縁取る。B は輪郭を 黒/田 で近似し、窓の縁は ×※ 系の文字になる。

**現在のまとめ**: A = 「速い・筋が通っている・のっぺり」。B = 「濃度と形は画像に
沿う・遅い・平滑域のテクスチャが粗い」。 方式の取捨はこの違いを
実機写真・実機 fps で確認してから決める。

## 実装上の発見（試作で判明した落とし穴）

基準実装を作る過程で、素直な実装が壊れるポイントを 4 つ確認した。
Web 側（GPU 含む）で同じ罠を避けるためのメモ:

1. **エッジ検出はセル平均勾配では検出できない**: 細いエッジ（幅 2px 程度）は
   セル平均で 1/fs に希釈される（0.7 のステップ → 平均 0.09）。セル内**最大**
   |勾配| を使う（ステップ → ≈ コントラスト、滑らかな勾配 → ≈ コントラスト/fs と
   分離できる）
2. **線分強度のセル集約は最大値を使う**: 「中心線 − フランク線」型の線検出
   フィルタはカーネル総和が 0 なので、セル**平均**は常に ≈ 0 になる
   （線上の正応答と周囲の負応答が相殺）。**セル内最大応答**で集約する
3. **方向ごとの正規化は等方性が必要**: 離散グリッド上の「硬い細線」を基準にすると
   水平/垂直（0.79）と斜め（0.33）で応答が乖離し、斜めの文字が過大評価される。
   カーネル自身のガウス・リッジ（ピーク 1.0）を基準にするマッチドフィルタ型の
   正規化でほぼ等方になった（0.42〜0.51）
4. **平滑セルで線文字を除外する**: 線文字は濃度が低く（0.03〜0.22）dir8 の
   コストも小さいため、除外しないと平滑な中間調が線文字に吸われ、画面が
   すじ状のノイズになる。dir8 最大値 < 0.15 のセルでは dir8 を比較せず
   線文字も候補から外す

### ユーザーの所見（15 枚すべて）

**A の輪郭検出について**:

- face1: 顔の輪郭はよく検知。ただし背景と服の色が近い部分で一部途切れる。
  髪と額の間のエッジは検出できていない
- face2: 顔の内部の検出は良好。ただし髪の光沢や服の柄に過剰反応
- face3: 背景と服の輝度が似ている部分のエッジ検出ができていない
  （元画像では色が違うため、grayscale 化を変えれば改善の可能性）。
  流れる長い髪のエッジが途切れ途切れ
- high_contrast1: 手と影の間のエッジを検出できず、手＋影を一つの輪郭で囲う
- high_contrast2: みかんの輪郭は問題なし。布のしわが途切れ途切れ
- high_contrast3: 問題なし。room1 / room3 / scene1 / scene5 も問題なし
- high_contrast4: 外枠のエッジが途切れ途切れ。内部の細かい輪郭も捉えられない
- room2: 輝度が近いオブジェクトが重なると一つの輪郭にまとめられる
- scene2: 細すぎる線はエッジとして検出されない
- scene3 / scene4: 夜景は建物も空も暗く色が近いため、エッジ検出が機能しない

**B について**:

- 平滑域の反復テクスチャは気にならない。むしろ散在するノイズ文字のほうが目立つ
- 形の追従は **A のほうが良い**。B は色の近い複数のオブジェクトが同じ模様で
  塗られて一つに混合しがち

**80 列の文字サイズ感**: 全体的に「もう少し細かくてもいい」。

### エージェントの所見（10 枚を閲覧: face1–3 / room1–2 / high_contrast1,2,4 / scene1,3）

- face1: A は顔の輪郭を線文字の連鎖で明瞭に描く。B は顔全体がなだらかな
  濃度表現になり、目鼻の構造が弱い。髪の黒塊内に白文字のノイズ点が散在
- face2: A は眉・ひげの輪郭は読めるが、セーターの柄に線文字が過剰反応。
  B は顔・髪・服が濃度塊に融合し、顔の構造がほぼ失われる
- face3: A は目鼻口の輪郭が明瞭で顔が最も読み取れる。B は顔の器官が溶け、
  髪と背景が融合して判読性が落ちる
- room1: A はモニタ・キーボード・ヘッドホンの物体輪郭が明瞭（全体で最も
  読みやすい組合せ）。B は全面が 反復テクスチャ になり物体境界がほぼ消失
- room2: A は輝度の近い物体が 1 輪郭にまとわれる（ユーザー所見どおり）。
  B は 黒/田 の反復が支配的で、物体の区別がさらに弱い
- high_contrast1: A は手＋影が 1 つの輪郭にまとめられ、壁の質感に散在ノイズ。
  B は手・影・壁が濃度差だけで輪郭情報が消える
- high_contrast2: A はみかん輪郭を ╱ ╲ の連鎖で捉え、布のしわは断片的な線片。
  B はみかんが淡い塊になるが、布のしわ構造はほぼ消失（濃度が近いため）
- high_contrast4: A は外枠が途切れるが内部グリッド・ボタン枠の一部は残る。
  B は手書き図面がほぼ完全に消失し、紙の陰影のグラデーションだけになる。
  **この画像での判読性は A の圧勝**
- scene1: A は右側建物の窓・屋根線を捉えるが、左側の暗い建物は暗い雲に融合。
  B は空のグラデーションは滑らかだが建物が黒塊化する
- scene3: A は窓枠・手すりの線を捉えるが暗部の境界が消え、明部の窓が断片的。
  B はほぼ全体が黒系文字の反復で、夜景の構造がほぼ読めない

### 合成画像との逆転（重要な発見）

合成画像では B が「濃度と形が画像に沿う」と評価されたが、**実機写真では
この利点が消え、A のほうが形を捉える**という逆転が起きた。考えられる原因:

1. 実機写真はテクスチャ・ノイズが多く、25 次元の距離では濃度の近いセルが
   同じ文字に寄集まる（形より濃度が支配する）
2. featurePx = 16 への縮小で細部が失われ、region4 の差別化力が低下する
3. 合成画像は「形と濃度が一致」していたが、実写真では一致しない
   （例: しわ・光沢は濃度差が小さく形の情報が弱い）

B の弱点（平滑域の反復・ノイズ・物体の混合）は合成画像で指摘していたより
実機写真では顕著に出た。

## 結論

- [x] **方式の採否: 方式 A を採用**（docs/decisions/D-009-glyph-selector-a.md）。
      実機写真での見た目は A が形の追従で明確に優り、B の利点（合成画像で見られた
      「形が沿う」）は実機写真では再現されなかった。計算量差（約 11〜12 倍）を
      払って B を採る理由がない。B は将来の GPU 実験での選択肢として方式自体は残す
      （25 次元距離計算が GPU で無料に近くなる場合に限り再評価する価値がある）
- [x] B を採る場合の調整 → **不採用のため取り下げ**（平滑域の反復テクスチャ対策、
      重みの再チューニングなどの項目は、再評価する場合の着手点として本書に記録済み）
- [x] A を採る場合の調整（Web 実装・チューニングの着手点として以下を記録）:
  - **輝度が近い領域の輪郭途切れ**（face1/face3/high_contrast1）: エッジしきい値
    0.14 の引き下げ、または局所コントラスト正規化を検討
  - **テクスチャへの過剰反応**（face2 のセーターの柄・髪の光沢）: 細かいテクスチャの
    セルではエッジ置換を抑制する（局所分散での抑制候補）
  - **暗部同士の境界消失**（scene3/scene4 の夜景）: 前処理にガンマ補正または
    明度ヒストグラム調整を足す候補。grayscale 化の前のカラー情報の利用も候補
    （face3 のユーザー所見）
  - **細すぎる線の非検出**（scene2）: featurePx（16）の引き上げ候補。ただし計算量増
  - **解像度感**（「もう少し細かくてもいい」）: 列数 100〜120 を Web 版の既定候補に
    加える。P-1 / P-2 との兼ね合いは EXP-1 の実機 fps の持ち越し事項と合わせて判断
- [x] 実機写真（data/ 配下）での再計測 → 上記「結果 3」。処理時間は合成画像と
      同傾向（B = A の約 11〜12 倍）。実機写真ではセル数の多い縦長画像で描画も
      22〜85 ms に増えるため、120 列相当では描画コストも見ておく

判断の詳細は docs/decisions/D-009-glyph-selector-a.md を参照。
